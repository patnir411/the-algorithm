🎯 Candidate Sources

All tweet candidate sources and generation strategies

📊 Overview: The Candidate Generation System

Twitter's recommendation system fetches tweet candidates from 10+ different sources running in parallel. These sources fall into two main categories:

In-Network Sources ~50% of candidates
Out-of-Network Sources ~50% of candidates
Total Candidates 1,500-4,000
Parallel Sources 10+
💡 Key Concept: In-network candidates come from accounts you follow. Out-of-network candidates are discovery content from accounts you don't follow, often shown with social proof like "Liked by @username".

🔵 In-Network Sources

These sources fetch tweets from accounts the user follows.

1. Earlybird Search Index IN-NETWORK

Real-time search index based on Apache Lucene. The primary source for in-network content, providing ~50% of all candidates.

📁 /home-mixer/product/scored_tweets/candidate_source/EarlybirdRealtimeCGTweetCandidateSource.scala
📁 /src/java/com/twitter/search/earlybird/

Architecture

Indexing Pipeline

  • Kafka stream → Ingesters → Feature extraction
  • Write to Earlybird shards (partitioned index)
  • Feature Update Service updates engagement counts
↓

Query Pipeline

  • User's followed accounts → Seed set
  • Query: tweets from seed users (7-day window)
  • Earlybird Root → Fanout to shards
  • Merge results with relevance scoring
Index Window 7 days
Throughput 50+ RPS/shard
Latency ~50-100ms
Typical Output ~800 tweets

Features Indexed

  • Static: Tweet text, media URLs, entities, language, author reputation
  • Real-time: Favorite count, retweet count, reply count (updated continuously)
  • Derived: Text quality score, engagement velocity, age normalization
  • Safety: NSFW flags, spam scores, abuse labels

Scoring Algorithm

EarlybirdScore =
  recencyScore × recencyWeight +
  reputationScore × reputationWeight +
  textScore × textScoreWeight +
  engagementScore × engagementWeight +
  socialProofScore × socialProofWeight

// Time decay applied
recencyScore = exp(-tweetAge / decayHalfLife)
2. User-Tweet Graph (UTG) IN-NETWORK

In-memory bipartite graph connecting users to tweets via engagement actions. Built on GraphJet framework.

📁 /cr-mixer/similarity_engine/TweetBasedUserTweetGraphSimilarityEngine.scala
📁 /src/scala/com/twitter/recos/user_tweet_graph/

Algorithm: Co-Engagement Based

Step 1: Find Co-Engagers

Given: Seed tweet T
Find: Users who engaged with T
  engagedUsers = UTG.getLeftNodeEdges(T)
  Filter: Only users who engaged via [Favorite, Retweet]

Step 2: Find Related Tweets

For each user U in engagedUsers:
  relatedTweets += UTG.getRightNodeEdges(U)

Group by tweetId:
  cooccurrence[tweetId] = count(users who engaged with both T and tweetId)

Step 3: Score Candidates

For each candidate tweet C:
  score = cooccurrence[C] / log(degree(C))

Filter:
  cooccurrence >= minCooccurrence (default: 3)
  degree(C) >= minResultDegree (default: 50)
Graph Window 24-48 hours
Min Co-occurrence 3 users
Update Frequency Real-time (Kafka)
Typical Output ~200-300 tweets

4. UTEG (User-Tweet-Entity-Graph) OUT-OF-NETWORK

The primary out-of-network source. Provides "Liked by [your connections]" recommendations based on GraphJet.

📁 /cr-mixer/candidate_generation/UtegTweetCandidateGenerator.scala
📁 /src/scala/com/twitter/recos/user_tweet_entity_graph/

How UTEG Works

Step 1: Seed User Selection

Fetch users from RealGraph or followed users

Input: User ID Output: ~100-200 seed users
↓

Step 2: Graph Traversal

Find tweets that seed users engaged with (favorites, retweets)

Engagement window: 48 hours
↓

Step 3: Social Proof Aggregation

Track which connections engaged with each tweet

Max social proof: 10 users per tweet
↓

Step 4: Filtering

  • Age filter (default: 24-48 hours)
  • Social proof types (Favorite, Retweet, Reply)
  • Tweet types (Regular, Photo, Video, not Retweet)
  • Direct interactions (exclude user's own content)
Graph Window 48 hours
Social Proof Max 10 users
Update Type Real-time (Kafka)
Typical Output ~200 tweets
🔑 Why UTEG is Powerful:
  • Social Proof: Shows which connections engaged → increases trust
  • Real-time: Fresh content updated every few seconds
  • Network Expansion: Discovers new accounts via your network
  • High Engagement: Pre-filtered by engagement from trusted connections
5. SimClusters ANN (TWISTLY) OUT-OF-NETWORK

Embedding-based recommendations using approximate cosine similarity across 145,000 communities.

📁 /cr-mixer/similarity_engine/SimClustersANNSimilarityEngine.scala
📁 /simclusters-ann/server/src/main/scala/com/twitter/simclustersann/

Algorithm: Approximate Cosine Similarity

Traditional Approach (Infeasible)

For 15,000 candidate tweets:
  Fetch full embedding (200 dimensions)
  Compute cosine similarity with user embedding
  → 15,000 embedding fetches = Too expensive!

Approximate Approach (Efficient)

Step 1: Source Embedding
  userEmbedding = Top 50 SimClusters for user

Step 2: Candidate Fetching
  For each cluster C in userEmbedding.top(50):
    topTweets[C] = Get top 400 tweets for cluster C
  → ~900 total candidates (50 clusters × ~18 unique tweets)

Step 3: Approximate Matrix
  Build sparse matrix with only top 50 clusters
  Other clusters set to 0

Step 4: Dot Product Calculation
  approximateScore = userEmbedding · candidateApproxEmbedding

Step 5: Top-K Selection
  candidates = Top 200 by approximateScore

Step 6: True Cosine Similarity
  For each candidate in top 200:
    Fetch full embedding (200 dimensions)
    trueScore = cosine_similarity(userEmbedding, candidateEmbedding)

Step 7: Threshold Filtering
  finalCandidates = candidates where trueScore >= 0.7

Efficiency: Only fetches ~900 embeddings instead of 15,000 (6% of brute force!)

Communities 145,000
Cosine Threshold 0.7
Throughput 6,000+ RPS
Typical Output ~150-200 tweets

Normalization Methods

Method Formula Use Case
Cosine Similarity score / (||user|| × ||tweet||) Standard similarity
Log-Cosine score / (logNorm_user × log(1 + norm_tweet)) Reduces popularity bias
Dot Product score Raw score without normalization
No Source Norm score / ||tweet|| Only normalize by tweet

🎛️ Source Orchestration: CR-Mixer

The Content Recommender Mixer (CR-Mixer) orchestrates candidate generation from multiple sources.

📁 /cr-mixer/candidate_generation/CrCandidateGenerator.scala
📁 /cr-mixer/candidate_generation/CandidateSourcesRouter.scala

Stage 1: Source Signal Extraction

Fetch user signals and preferences:

  • Real Graph In/Out-of-Network scores
  • User Signal Service (USS) - recent favorites, RTs
  • FRS - follow recommendations
↓

Stage 2: Candidate Generation (Parallel)

Route to appropriate similarity engines:

  • Tweet-Based: UTG, UVG, SimClusters ANN, QIG, TwHIN
  • Producer-Based: Real Graph, FRS, SALSA
  • Consumer-Based: WALS, Ad Graph, Video Graph
↓

Stage 3: Filtering

Pre-rank filters:

  • Exclusion filters (blocked, muted authors)
  • Age filters (tweet recency)
  • Negative signals (reported, hidden)
↓

Stage 4: Blending

Mix candidates from different sources:

  • Round-Robin: Interleave sources
  • Source Type Back-Fill: Priority ordering
  • Content Signal Sorting: By recency or score
↓

Stage 5: Light Ranking

Fast ML-based pre-ranking to reduce to ~1,000 candidates

↓

Output to Home-Mixer

Ranked candidates ready for heavy ranking

🔑 Key Insights

Why Multiple Sources?

  • Coverage: Different sources capture different aspects of relevance
  • Freshness: Real-time sources (Earlybird, UTEG) + batch sources (SimClusters)
  • Diversity: In-network familiarity + out-of-network discovery
  • Redundancy: Fallback if one source fails or underperforms
  • Specialization: Video-specific, community-specific, embedding-specific

Parallel Execution Strategy

All sources run simultaneously using Scala's Stitch framework for async execution. Total latency = max(individual source latencies), not sum!

Total Latency ≈ 100-200ms
  = max(
      Earlybird: 50-100ms,
      UTEG: 50-80ms,
      SimClusters: 80-120ms,
      FRS: 100-150ms,
      ...
    )

Source Weighting

While all sources contribute candidates, their implicit weights differ:

  • Earlybird: Highest volume (~800 tweets) → Dominates in-network
  • UTEG: High quality with social proof → High conversion
  • SimClusters: Long-tail discovery → Helps diversity
  • FRS: Author discovery → Network growth
